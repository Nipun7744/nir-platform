# Database — NIR Platform

> Schema reference and design decisions. Update whenever a migration lands or a model changes.
> Source of truth is always `apps/api/prisma/schema.prisma` — this file explains it, doesn't
> replace it.

## Overview

- **PostgreSQL 16**, accessed exclusively through **Prisma ORM**
  (`apps/api/src/prisma`, schema at `apps/api/prisma/schema.prisma`).
- **47 models**, **23 enums**, organized in the schema file by SRS component (see section
  headers/comments in `schema.prisma` itself).
- IDs are `cuid()` strings everywhere. `Innovation` additionally carries a human-readable unique
  `innovationCode` (e.g. `NIR-2026-000123`); `Innovator` carries a unique `irn`
  (`IRN-2026-000123`) — both generated by `IdGeneratorService`.
- **Bilingual fields are parallel columns** (`titleEn`/`titleBn`, `summaryEn`/`summaryBn`, ...)
  rather than a separate translations table — see [PROJECT_CONTEXT.md](PROJECT_CONTEXT.md#important-decisions)
  for the tradeoff.
- `Evaluation.scores` is stored as `Json` (rubric criterion → score map) rather than normalized
  into rows — trades queryability for flexibility across different evaluation rubrics.
- Local Postgres in this dev environment runs on **`localhost:5433`** (mapped from the container
  default 5432 to avoid clashing with any other local Postgres) — see [SETUP.md](SETUP.md).

## Models by domain

### Identity, Auth, RBAC, Audit (cross-cutting)

- **`User`** — central identity. `roles: Role[]` (default `[PUBLIC_VIEWER]`), `locale`,
  `isActive`/`rejectedAt` (registration approval gate — see [API.md](API.md#auth)),
  `evaluatorCategoryIds` / `preliminaryReviewerCategoryIds` / `authenticityReviewerCategoryIds`
  (String arrays of `Category.id`, one per specialization role). Optional 1:1 profiles:
  `innovatorProfile`, `investorProfile`, `mentorProfile`, `ministryProfile`.
- **`RefreshToken`** — `tokenHash` (unique, SHA-256), `expiresAt`, `revokedAt`. Cascades on
  `User` delete.
- **`AuditLog`** — `actorId?` (nullable, `SetNull` on user delete so history survives),
  `action`, `entityType`, `entityId?`, `metadata: Json?`, `ipAddress?`. Indexed on
  `[entityType, entityId]`, `actorId`, `createdAt`. Written via `AuditLogService.record` from many
  modules (see grep for call sites) but had no read endpoint until the Admin Repository
  Management module (2026-08-17) added `InnovationsService.listActivityLog`, exposed at
  `GET /innovations/:id/activity-log` (one innovation) and `GET /innovations/admin/activity-log`
  (all `entityType: 'Innovation'` entries) — see [API.md](API.md#innovations-innovations).
  `InnovationsService.addAttachment`/`removeAttachment`/`replaceAttachment` now also record
  `INNOVATION_MEDIA_UPLOADED`/`_REMOVED`/`_REPLACED` entries; they didn't before this module
  existed.

### Reference data (admin-managed lookups)

`Category` (icon + bilingual name/description/examples, `slug`), `SdgTag` (UN SDG 1–17),
`Tag` (`THEMATIC`/`TECHNOLOGY`, unique per `[type, nameEn]`), `Region` (self-referential
`DIVISION`/`DISTRICT` hierarchy via `parentId`), `Ministry` (`code`, bilingual name).

### Component 1 — Innovation Submission & Evaluation

- **`Organization`** → **`Innovator`** (1:1 with `User`, has `irn`, optional org link,
  `nidVerified`) → **`Innovation`** (the central entity: bilingual title/summary, problem
  statement, TRL 1–9, `innovationType`, `developmentStage`, `ipStatus`, `fundingSource`,
  `reviewStatus`, `rejectedAtStage` (nullable `ReviewStage`; which stage's reviewer rejected it —
  see below), `authenticityReviewedById` (nullable plain user-id field; which Authenticity Reviewer
  shortlisted it — see below), `pipelineStage`, geo (`lat`/`lng`), links to
  `Category`/`Region`/`Organization`/`Ministry`/`MinistrySubmissionCycle`; plus three independent
  "support requested" boolean flags set by the submitter on the submission form — `mentorshipNeeded`,
  `fundingNeeded` (migration `20260730044929_add_mentorship_funding_needed_flags`), and
  `recognitionNeeded` (migration `20260810093247_add_recognition_needed_flag`, added 2026-08-10) —
  each `@default(false)`, surfaced read-only as "Support requested" badges on the evaluator's
  innovation-detail view and the submitter's own manage-innovation page).
- **`Innovation` admin approval fields** (migration `20260811100354_add_admin_approval_fields`,
  added 2026-08-11) — one boolean + comment pair per support type requested above:
  `recognitionApproved`/`recognitionApprovalComment`, `mentorApproved`/`mentorApprovalComment`,
  `fundApproved`/`fundApprovalComment` (each boolean `@default(false)`, comment nullable), plus a
  single shared `approvalLetterUrl` (nullable) covering whichever of the three were approved —
  deliberately *not* three separate letter fields, since one letter can cover multiple approvals.
  Not gated on the sibling `*Needed` flag at the schema/service level (an admin can still record a
  decision even if the request was edited after the fact) — the gating is UI-only: the admin's
  Permission & Approval section (`PATCH /innovations/:id/approval`, see [API.md](API.md)) only
  shows/submits the fields whose `*Needed` flag is true, in the order Recognition → Mentor → Fund.
- **`InnovationTeamMember`** (M:N-ish join with a display name/role, optionally linked to an
  `Innovator` or bare `User`), **`InnovationAttachment`** (`AttachmentKind`), **`InnovationTag`**
  / **`InnovationSdgTag`** (join tables, composite PK), **`SuccessStory`** (1:1), **`Award`**.
- **`EvaluationPanelAssignment`** (unique per `[innovationId, evaluatorId]`) →
  **`Evaluation`** (unique per `[innovationId, evaluatorId]`, `scores: Json`, `isBlind`).
- **`IpAdvisoryFlag`** — evaluator/coordinator-raised IP concern.
- **`ReviewComment`** — full history of Preliminary/Authenticity reviewer notes (`ReviewStage`),
  deliberately separate from `Innovation.reviewRemarks` (latest-only) so context survives
  reject/resubmit cycles.
- **`Innovation.rejectedAtStage`** (nullable `ReviewStage`, added 2026-08-09) — set by
  `InnovationsService.updateStatus` whenever `reviewStatus` transitions to `REJECTED`, derived from
  the *from* status (`UNDER_REVIEW` → `PRELIMINARY_REVIEW`, `AUTHENTICITY_REVIEW` →
  `AUTHENTICITY_REVIEW`, anything else → `null`), regardless of which role's account performed the
  transition. Cleared back to `null` on any transition away from `REJECTED` (including resubmit via
  `submit()`). Exists so each reviewer stage's "Rejected" tab can show only rejections it's
  actually responsible for — without it, both Preliminary and Authenticity Reviewer queues showed
  *every* `REJECTED` innovation in their assigned categories, regardless of which stage rejected
  it, which was confusing (a submission the Authenticity Reviewer never touched could appear in
  their Rejected tab just because the Preliminary Reviewer rejected it in a shared category). See
  [API.md](API.md#api-changes) and [ROADMAP.md](ROADMAP.md#completed).
- **`Innovation.authenticityReviewedById`** (nullable, added 2026-08-09) — a plain user-id field
  (no formal `@relation`, matching `submittedById`'s existing pattern on this model, to avoid
  growing `User`'s already-long back-relation list for every FK that references it). Set to the
  acting user's id by `InnovationsService.updateStatus` on the `AUTHENTICITY_REVIEW → SHORTLISTED`
  transition specifically, left untouched on every other transition (including later
  `SELECTED`/`PUBLISHED` moves made by other roles) so it keeps attributing to the original
  reviewer. Exists because a `Category` can have multiple Authenticity Reviewers assigned —
  category-only scoping (as `rejectedAtStage` above uses) isn't enough to show one reviewer only
  *their own* shortlists on the "Reviewed" tab, since it would also show every other reviewer's
  shortlists in the same category. Nullable and left `null` for innovations whose `SHORTLISTED`
  status was seeded directly rather than reached through the real review flow (no genuine reviewer
  to attribute to).

### Component 2 — Funding Matchmaking

`Investor` (1:1 `User`, `binNumber`/`binVerified`, `sectorInterestIds: String[]`) →
`ExpressionOfInterest` (`EoiStatus`), `InnovationReferral` (evaluator → investor, unique per
`[innovationId, investorId]`), `FundingAgreement`, `FundDisbursement` (`Decimal(14,2)`,
`FundingSource`, `recordedBy: User`).

### Component 3 — Repository & Search

`SavedSearch` (`userId`, `label`, `queryJson: Json`) — the only model here; search itself is
service-layer `ILIKE` queries, not a dedicated search index/model (see
[PROJECT_CONTEXT.md](PROJECT_CONTEXT.md#important-decisions)).

### Component 4 — Communication & CMS

`ContentItem` (`ContentType`, `ContentStatus`, `authorId`) → `ContentRevision` (JSON snapshots),
`NotificationTemplate` (bilingual subject/body per channel/code), `Notification` (per-user
delivery record), `MediaAsset`, `FaqItem`, `FeedbackGrievance` (nullable `userId` — anonymous
feedback allowed), `NewsPost`, `ResourceDocument` (`ResourceType`), `Challenge`
(`ChallengeStatus`, `isFeatured: Boolean @default(false)`, `startDate`/`deadline` — the timeline
shown publicly; `deadline` doubles as "end date"; `bannerImageUrl: String?` — same upload flow as
`NewsPost.coverImageUrl`, via `POST /uploads`), `Partner`.

`Challenge.isFeatured` is enforced single-valued at the service layer, not the schema: whenever
`createChallenge`/`updateChallenge` sets `isFeatured: true` on one row, it first `updateMany`s
every other `Challenge` to `isFeatured: false` in the same call (see
`cms/public-content.service.ts`). Public UI (homepage banner, the site-wide "running challenge"
popup) picks, among `status: OPEN` challenges, the featured one first, falling back to the first
OPEN challenge if none is featured — see the CMS section of [API.md](API.md) and
[UI_GUIDELINES.md](UI_GUIDELINES.md).

### Component 6 — Mentorship

`Mentor` (1:1 `User`, `expertiseTagIds: String[]`) → `MentorMatch` (unique per
`[mentorId, innovationId]`), `MentorSession` (`SessionMode`/`SessionStatus`) → `MentorFeedback`
(1:1 per session, `rating` 1–5), `MentorActivityLog` (hours logged).

### Component 7 — Internal Pipeline

`PipelineNote` — free-text notes + optional attachment against an `Innovation`, authored by a
`User` (Innovation Manager / Coordinator / Admin).

### Component 8 — Ministry Reporting

`MinistryFocalPoint` (1:1 `User`, linked to a `Ministry`) → `MinistrySubmissionCycle` (yearly,
unique `year`, `opensAt`/`closesAt`) → `MinistrySubmission` (unique per `[ministryId, cycleId]`,
`MinistrySubmissionStatus`) → `MinistryAnnualReport` (generated artifact, `fileUrl`,
`stats: Json`).

## Seeding

`apps/api/prisma/seed.ts`, run manually: `npx ts-node prisma/seed.ts` (local) or
`docker compose exec api npx ts-node prisma/seed.ts` (Docker). Populates reference data
(categories, SDG tags, regions, ministries) and the demo accounts listed in
[PROJECT_CONTEXT.md](PROJECT_CONTEXT.md#demo-accounts). Re-running it is expected to be
idempotent for lookups (upserts) — verify before assuming that holds for anything new you add.

## Schema design decisions

See [PROJECT_CONTEXT.md § Important Decisions](PROJECT_CONTEXT.md#important-decisions) for the
narrative version of: enum-based controlled vocabularies instead of separate lookup tables where
the set is fixed by the SRS; bilingual parallel columns instead of a translations table; `Json`
for the evaluation rubric instead of normalized rows.
